# T07b review — app security (D21, D22, D19) + connector discovery (D18) (fresh reviewer; code read, gradle not run)

**Checked and holding.**
- D21 path: every tailnet client goes through `forEndpoint` → `TailnetSocketFactory`, which checks for a VPN on every new socket and calls `Network.bindSocket` before connect. A pooled socket bound to a VPN that has gone away fails; it never moves to Wi-Fi or cellular. No DNS: hosts are IP literals (`inetAddress` from bytes, OkHttp `getByName` on a literal). The WebSocket upgrade keeps the client's socket factory and interceptors (ws:// → guard + VPN). The pair probe runs only for LAN. Tailnet pairing goes through `HttpPairingApi` → bound factory. `Proxy.NO_PROXY` is set on base + every `forEndpoint` client, and `Socket(Proxy.NO_PROXY)` in `DirectSocketFactory` and the probe. `TailscaleOffException` is found in cause/suppressed. If the app is excluded from Tailscale (split tunnel), `bindSocket` fails and nothing is sent.
- D22: only bad tag, missing key, invalidated key, IAE/SerializationException (bad entry) or an absent entry cause a wipe. KeyStoreException, ProviderException, IllegalBlockSizeException and UnrecoverableKeyException caused by a daemon error keep the entry → `Unavailable` page with Retry and Pair again. Decrypt never creates a key. load/save/wipe run on IO behind one Mutex with `commit=true`. A failed save gives `StoreFailed`, not a crash. `parseIpv6` is pure (no platform call). `SessionRepository` gets 7 fake-socket tests (4401, /me 401 without a socket, ready timeout, debounce, list guard, list error, 4503). `onMessage` only does `trySend` into an unlimited buffer, so it never blocks OkHttp's reader (new §12 client rule). The 3 security tests and the 4 NITs are present (`surfaceContainerHighest`, `liveStatus`, `!id.isString`, ASCII hex). `RouteStores` clears the old route's store.
- D19: `DeviceName.of(Settings.Global.DEVICE_NAME, …)`, trimmed, fallback without a duplicated maker. Fine.
- D18 vs Hermes source: matches `discover_gateway_endpoint` (fallback only on ENOENT/ECONNREFUSED → `_served_by_multiplexer`), `multiplexer_root_for` / `named_profile_home` (`profiles` parent, no leading dot, root `.hermes` or a marker or `profiles/.deleted`), `_endpoint` (exactly one served entry for this home, non-empty id) and `control_home_for` (tickets are minted on the root socket that answered: `controlPath`). The root's socket still gets SO_PEERCRED. Not served → `ErrHermesNotRunning`, nothing minted (test). Files stayed in scope. No relay files touched.

**MAJOR (unproven)** `data/AndroidVpnRoutes.kt:27-32`: "a VPN network routes the address" is not the same as "Tailscale is up". A full-tunnel VPN that is not Tailscale (commercial, work, Cloudflare WARP) has 0.0.0.0/0 (and ::/0), so `routes.any { it.matches(address) }` is true. Android runs one VPN at a time, so Tailscale is off whenever that VPN is on. In that case the app sends the pairing code and the Bearer token (`/v1/me`, the `/v1/ws` upgrade) in cleartext into that VPN, to whoever holds 100.x on the VPN's far side. That is the T07 CGNAT threat again, one hop further away. `RouteInfo.matches` also ignores the route type (an excluded THROW route still matches). Test gap: `AndroidVpnRoutes` has no test (the fake `VpnRoutes` hides it). Fix: accept a VPN only when (a) a route with prefix length > 0 covers the address (Tailscale with an exit node still carries 100.64/10 or the peer routes), and (b) its `LinkProperties.linkAddresses` include an address in 100.64.0.0/10 or fd7a:115c:a1e0::/48 (Tailscale's own node IP). Put this check behind a seam and test it. This narrows the gap; it does not close it (WARP uses 100.96/12). The real cure is to stop trusting the network for the token: pin TLS on the tailnet listener too. That is a PM/protocol decision before T09/T10 make reconnects unattended.

**MINOR (unproven)** `KeystoreTokenKey.kt:21,37-40` + `CredentialCodec.kt:69`: on API 29-30 (minSdk 29, keystore1), `AndroidKeyStoreSpi.engineGetKey` returns null when `KeyStore.contains` fails. `contains` returns false on a binder `RemoteException`, so a restarting keystore daemon becomes `TokenKeyMissingException` → permanent → the pairing is wiped. This is exactly the transient case D22 targets. Keystore2 (API 31+, the Poco) is fine (null only on KEY_NOT_FOUND). Fix: on SDK < 31, treat a missing key as `Unavailable` once per process (or until a second read), or confirm with `KeyStore.containsAlias` after a reload.
**MINOR** `server/internal/hermes/control.go:138-141` (`resolveProfile`): `""` and `"default"` both pick the launch profile. With `HERMES_HOME=profiles/pm` the launch profile is now pm, so a phone that asks for the profile literally named `default` gets pm. Before, the launch profile was the root, so the two agreed. Make `"default"` resolve to the served entry whose home is the root (`c.root`/`HermesHome`) and keep `""` = launch profile, or write the alias into protocol.md §1.1 before T14 (profile switch) relies on it. The rest of the "launch profile becomes pm" consequence is as intended and documented in §1.1: Dial/Do tickets bind to pm (test `TestProfileHomeWithoutSocketUsesTheRootGateway`), and systemd without `HERMES_HOME` is unchanged.
**MINOR (latent)** `data/HttpClients.kt:53-54`: every client shares `base`'s ConnectionPool, and OkHttp 5.4.0 `Address.equalsNonHost` does not compare `socketFactory` (checked with javap). A cleartext 100.x client built anywhere but `forEndpoint` would reuse VPN-bound connections, and the reverse also holds. That is safe today. Note it in the `HttpClients` KDoc, or give tailnet clients their own `ConnectionPool`.

**NIT** `discover.go:22-25`: Hermes resolves `profile_home` (`_canonical_home`) before `multiplexer_root_for`. Here only `filepath.Clean`, so `HERMES_HOME` given as a symlink to a profile is not followed. Markers use `Lstat`, where Hermes uses `exists()` (follows links).
**NIT** `discover.go:71-78`: `serves` counts only entries with a non-empty id. Hermes counts every entry for the home and then requires the single match to have an id, so a duplicate entry with an empty id passes here and fails in Hermes. `launchProfileID` (control.go:119-124) then returns the first match, which could be that empty id.
**NIT** `TailnetRoute.kt` / `ConnectionPage`: when Tailscale is up but no route covers the address (a stale 100.x, per-peer routes), the app says "Tailscale is off". The copy could say "Tailscale does not reach this address".
**FYI** Device behaviour of D21 is not verified (build report). PM to check on the Poco: Tailscale off → page; Tailscale on → list; a non-Tailscale VPN on → should refuse, but per the MAJOR it currently sends.

VERDICT: PASS-WITH-FINDINGS
