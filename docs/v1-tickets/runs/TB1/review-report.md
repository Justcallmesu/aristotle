# Review — TB1 (Q77 status stack, process.list/kill) + TR minors 1-5

Scope: `git diff HEAD -- android CHANGELOG.md docs` + untracked, briefs, Hermes source. pm-gate-55 GREEN (927). No device, no gradle.

**process.kill only from an armed Stop: holds.** The row's Stop calls `askStop` only (BackgroundControl.kt:281-286). Only `confirmStop` sends (:292-308): it needs `confirm != null`, `stopping == null` and 600 ms since `at` (:192-195), clears `confirm` synchronously through `state.updateAndGet` (ChatViewModel.kt:431-433), so a double tap sends once. The UI arm `remember(confirm)` + delay (StatusStack.kt:242-246) re-arms after rotation or unlock. Cancel, back and outside go to `cancelStop` (:250, :281). A stale dialog can't hit the wrong process: ids are `proc_<uuid12>` (process_registry.py:1093) and `methods_tools.py:292-294` returns 4044 for another session. A switched session gets a new VM (route key `chat-…-$sessionId`, AristotleApp.kt:407). A stale or offline Stop gives already_exited, not_found or NotSent, so it does no harm.
**Process id: correct.** The row's `session_id` is `s.id` (process_registry.py:2389), and that is what `process.kill` looks up via `registry.get(process_id)` (methods_tools.py:288-295). The Desktop sends the same (composer-status.ts:504).
**Result mapping: correct.** killed / already_exited / not_found / error+`error` (tools_commands.py:129-151, process_registry.py:521, :2216-2219); 4044 and 4001 map to NotFound, other codes to Failed (BackgroundProcesses.kt:93-112).
**Polling: correct.** Gates are visible + `ChatLive` + confirmed subscription + not latched (BackgroundControl.kt:177-180). ON_START/ON_STOP plus dispose for the app lock (ChatScreen.kt:132). 4001/4044 latch per generation (:269-272) and a resubscribe resets them, as the Desktop does. Events match the Desktop (tools.ts:195, status.ts:149). Every job runs in `viewModelScope`, so nothing leaks. `LinkService` makes no calls (grep). The relay forwards these methods as claimed.
**Subagent rows: correct.** The `live` filter is Queued|Running, the same as the Desktop (composer-status.ts:251). A tap calls `openSubagent(id)`, the T17 page.

**Findings**
- MAJOR-1 (composer hidden under the IME): StatusStack (ChatScreen.kt:325) is measured before Composer (:336), whose height includes the IME inset (Composer.kt:157). The cap is 40 % of the **window** (StatusStack.kt:99-100), not of the space left. Example on an 873 dp phone with the keyboard open and ≥5 rows: 349 dp stack + ~64 dp top bar + ~35 dp status bar leave ~425 dp, while the composer needs IME (~300-330 dp) + field. The field, waiting chip and slash menu get clipped, and the transcript gets 0 dp. Landscape is worse. Fix: measure the composer first (stack `Modifier.weight(1f, fill = false)` plus the cap), or cap against the Column's remaining height, or fold the stack while the IME shows. Then check on the Poco with the keyboard open. (Derived from Compose's Column measure order, not seen on a device.)
- MINOR-2: `killFailure` maps `linkClosed` to NotSent, "Not sent: the PC is not connected" (BackgroundProcesses.kt:107). But `failAll` sets `linkClosed` on calls that were already written (RelayRpc.kt:51-55), so the kill may have run. Say "unknown, check the list" when `written`.
- MINOR-3 (load): the phone polls every 5 s even with no running row; the Desktop polls only while one exists (status-stack/index.tsx:193-200). Every row carries `output_tail` ≤4000 chars (server.py:1919), and exited processes stay listed for 30 min (process_registry.py:63). So about 5 finished rows cost ~20 KB per poll, ~15 MB/h while the chat is open. Acceptable per the brief, but adopting the Desktop gate is suggested (PM decision).
- NIT: the dialog stays open after its row leaves or the link drops. It is harmless, but it could close itself. `armed` stays true when the screen comes back without recreation (StatusStack.kt:242).
- NIT: the waiting chip falls back to "approval" while an answer is in flight (ChatScreen.kt:352). During the busy-hint fade-out, the steady hint shows at once, so two lines appear briefly (Composer.kt:180-187).
