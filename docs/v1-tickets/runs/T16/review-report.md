That is accepted scope.
**2. Size math holds.** 783 360 B → base64 1 044 480 B. 4 096 B left for the envelope. A send-time check rejects a frame > 1 MiB − 512 (the 512 is kept for `profile`), measured with id = Long.MAX (`ChatComposer.kt:272,355`, `AttachFrames.kt:78`). Tests check the fit at the cap and an overflow (`AttachmentRulesTest.kt:20-36`). Phone frames go to Hermes untouched (`relay/session.go` `forward` → `hc.Write(frame)`); redaction only runs Hermes→phone. Hermes `/api/ws` allows 384 MiB (`web_server_boundary.py:26`). On a frame over the limit, `SetReadLimit` (`relay.go:109`) sends 1009 and the whole socket closes. That socket is the one LinkManager link, so every open chat drops and reconnects. The pre-check means the attach path can't trigger it → FYI.
**3. Retry and idempotency hold.** `stageAll` returns null before any submit (`ChatComposer.kt:235,261`), so a prompt never goes out without its attachments. Staged answers are reused (`:257-259`), and `afterSubmitFailure` re-stages images only, after Refused. Hermes treats a retry as the same admission by sha256 (`session_ingress_media.py:173-176`) and covers a pruned staging file with the committed row (`:165-171`). The payload digest makes a different text an `admission_conflict` (`hermes_state_runtime.py:151-159`). A re-staged file gets the `-2` name (`prompt_attachments.py:330-343`), so keeping `ref_text` is required, and the code keeps it. Send stays off while any item is preparing or refused (`ComposerState` `hasContent`).
**4. Privacy: the JPEG primary is correct.** The GPS IFD is found through IFD0 tag 0x8825. Its entries, the out-of-line data and the count are zeroed. Every Exif APP1 is handled, and XMP APP1 segments are removed (`ImageMetadata.kt:50-65,172-184`). IFD1 has no GPS pointer by spec. PNG eXIf/iTXt-XMP and WebP EXIF/XMP → re-encode. `Bitmap.compress` output also goes through the stripper. Sending PDFs and other documents as-is is acceptable: the user picked a document, and the Desktop sends originals.
**5. Android.** FileProvider exposes only `cache-path camera/`, is not exported, and grants per URI. The merged manifest (`build/intermediates/merged_manifest/debug/…:11-25`) has no CAMERA permission, so a bare TakePicture intent is allowed. ActivityNotFound is caught. There is no storage permission. Sending reads one item at a time, so only one base64 copy (~1 MB, ~3–4 MB with copies) is in memory at once. Preparation is the risk (MINOR-1).
**6. Timeout.** It is real only on a weak uplink (MINOR-4).

## Findings (no BLOCKER/MAJOR)
- **MINOR-1 Memory on a 10-photo pick.** `attach` launches every prepare at once (`ChatComposer.kt:78-81`) on Dispatchers.IO. Each one reads the source (≤64 MiB) into a growing `ByteArrayOutputStream` (2–3× transient), then decodes a ≈7 MB 1568-px bitmap (`AttachmentFiles.kt:110-116,130-142`). Ten 6 MB photos come to roughly 200 MB peak against a likely 256 MB heap. An `OutOfMemoryError` is not caught, so the app crashes. Fix: `limitedParallelism(1–2)`/Semaphore, and presize the stream from `meta.size`. Not run on the Poco.
- **MINOR-2 GPS outside the primary JPEG head.** The scan stops at the primary's SOS (`ImageMetadata.kt:80-82`). MPF / Ultra-HDR secondary images and vendor trailers after EOI keep any Exif GPS they carry. Extended-XMP APP1 (`ns.adobe.com/xmp/extension/`) is not removed (`:192`). I did not check whether the Poco camera writes these. Fix: re-encode when there is an APP2 `MPF` segment or bytes after the primary EOI.
- **MINOR-3 File picks are routed by MIME only.** `meta.type in IMAGE_TYPES` (`AttachmentFiles.kt:55,212`): a JPEG/TIFF/DNG that a provider labels `application/octet-stream`, `image/jpg` or `image/avif` goes byte for byte as a file, GPS included, and Hermes gets a file instead of an image. Fix: run `AttachmentRules.sniff` on File picks too.
- **MINOR-4 A 15 s RPC timeout covers the whole 1.04 MB write** (`RelayRpc.kt:18,28`). Below ~0.6 Mbit/s uplink (weak cellular, Tailscale DERP), each upload times out and shows "Couldn't upload X: the PC did not answer. Nothing was sent." Retry sends the same MB again and will likely fail again. A late frame can still land on Hermes and leave an orphan in `cache/images` or `attachments/`. Calls from other chats wait behind the frame on the shared socket. Fix: scale the timeout of staging calls with frame size.
- **NIT.** Prepared bytes are not deleted after a successful send, and a cancelled camera file stays behind. Both are pruned only on the next prepare (`AttachmentFiles.kt:195-199`). A GIF goes as-is and may carry an XMP application extension.

NOT-VERIFIED (same as the build report): nothing ran on the phone or against Hermes; HEIC decode memory with `setTargetSize`; profile-routed `image.attach_bytes` for sibling profiles (T14). I did not re-run the gate; I took pm-gate-29 GREEN and the PM mutation result as given.

VERDICT: PASS-WITH-FINDINGS
