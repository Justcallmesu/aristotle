# T16 build report — pictures and files from the phone

**How the Desktop attaches** (Hermes @717447e, read-only). Bytes not on the gateway's disk are staged over `/api/ws`, one message each, then submitted: images `image.attach_bytes {session_id, content_base64, filename}` (`apps/desktop/src/app/session/hooks/use-prompt-actions/index.ts:148,165-206`; owner handler `gateway/session_images.py:8-45`, PNG/JPEG/GIF/WebP only, writes `<profile>/cache/images`), files `file.attach {session_id, name, data_url}` → `ref_text` `@file:…` (`index.ts:209-230`; `gateway/session_ancillary.py:137-180`). Then `prompt.submit {text, submission_id, attachments:[{path,mime}]}`, text = `@file:` lines + `\n\n` + typed, or "What do you see in this image?" (`submit.ts:289-303,1080-1088`; admitted only from Hermes' staging dir, ≤10, `gateway/session_ingress_media.py:122-156`). The local Desktop stages images over REST `/api/chat/image-upload` instead (`upload-server-image.ts:34-40`). Both write Hermes' tree **by Hermes**; aristotle-server writes nothing. No chunked upload exists (`apps/desktop/src/store/updates.ts:114`). The Desktop sends originals (`utils.ts:515-537`).

**Transport chosen.** The Desktop's remote path over the existing relay; no server change, no new endpoint, relay limits untouched. Per message: N staging frames (in order) + 1 submit. Retry keeps the `submission_id`; staged answers are kept (a file's `ref_text` must not change or Hermes refuses the id); after a refused submit, images are staged again (Hermes matches retries by sha256, `session_ingress_media.py:158-181`). An upload failure means no prompt was sent ("Nothing was sent", Retry/✕); ✕ puts the text and attachments (with what was staged) back.

**Limits.** 1 frame ≤ 1 MiB ⇒ ≤ 783 360 bytes per item (`(1 MiB − 4 KiB)/4×3`), checked again on the built frame; ≤ 10 per message (Hermes' cap); far under 600 frames/min. Files over the cap and GIFs over the cap are refused on the chip with the size and the limit. Images: a JPEG that fits goes as it is with its **Exif GPS IFD blanked and XMP removed** (orientation and pixels untouched); PNG/WebP that fit and carry no Exif-GPS/XMP go as they are; everything else (too large, HEIC/HEIF — Hermes takes only png/jpeg/gif/webp, `session_ingress_media.py:122` — BMP, PNG/WebP with location) is decoded with ImageDecoder (applies orientation, reads HEIC) and written as JPEG from a 1568 px long edge (Hermes' own embed size, `tools/vision_tools.py:358-365`) down a ladder until it fits; no metadata. Why strip when the Desktop sends originals: phone photos carry GPS; desktop screenshots don't. The name's extension always matches the bytes (Hermes trusts it first, `tui_gateway/prompt_attachments.py:91-99`).

**UI.** Paperclip in the composer → Photo (PickMultipleVisualMedia, no storage permission), Take photo (ACTION_IMAGE_CAPTURE into `cache/camera/` via a non-exported FileProvider; merged manifest has no CAMERA permission, so none is needed), File (OpenMultipleDocuments; picked png/jpeg/gif/webp/heic go the image way, as on the Desktop). Chips above the field: thumbnail/icon, name, size or why refused, ✕; Send/Queue off while preparing or refused; Steer off with attachments (steer carries words only). Echo bubbles show per-attachment Waiting/Uploading/Uploaded/Upload failed. User rows (history and `pending`) are split like the Desktop's hydration (`hydration.ts:40-50,510-521`, `reference-kinds.ts:175-197`): native `[Image attached at: …]`+`[screenshot]` suffix, `@image:` lines, leading `@file:` block → image/file chips; own images show thumbnails (kept by sha256, which names Hermes' stored folder; also bridged by admission until the history shows them); Desktop-sent images show as named chips (the relay carries no file reads).
