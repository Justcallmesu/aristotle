# TL1 + TL1c + TM1 + TL1d security re-review (fresh, deep; read-only, no gradle/adb)
Paths: `android/app/src/main/java/.../aristotle/data/` unless noted. TL1d = `git show 584b7f4`.

## Previous findings: closed
- **MAJOR-1:** the /24 probe (AndroidLanDiscovery.kt:130-145) and every `/healthz` check (ServerClient.kt:100-106) use `WifiRoute`. Its sockets are bound through `DirectSocketFactory(bind)`, which closes the socket and throws if the bind fails (DirectSocketFactory.kt:13-22). DNS runs on the network (AndroidLanDiscovery.kt:89); hosts are IP literals anyway. The check is the pinned client's `newBuilder()`: same PinnedTrustManager/HostnameVerifier, NO_PROXY, TLS only, no redirects, its own pool with no idle connections, and no token. The gate (LanDiscovery.kt:59-70) requires Wi-Fi without a VPN, and a throwaway `bindSocket` must succeed (AndroidLanDiscovery.kt:86-90; netd SELECT_NETWORK EPERM, so the test is real). The route is bound again before the scan (:330). NSD discovery itself is not tied to a network (:171); see NIT.
- MINOR-1: announced hosts must be on-link for the route's Wi-Fi before any connection (LanDiscovery.kt:357). Closed.
- MINOR-2: found addresses are no longer stored on discovery. The found address is a one-shot candidate (EndpointChoice.kt:38, LinkManager.kt:213) and is stored only by `refreshAddresses` after `gateway.ready` (LinkManager.kt:356, 440). Closed. A forwarder still gets stored; see MINOR-A.
- MINOR-3: `ResolveSlot` frees the slot on the answer, on the 3 s wait, or on a 3 s timer (LanDiscovery.kt:377-403, AndroidLanDiscovery.kt:216, 239). Closed.
- MINOR-4 / TM1: checks carry ids, and a late `authEnded` is ignored (AppLock.kt:116-117). The cap timer is armed on the first check (:82-86); a stale timer finds `now-authStartedAt < cap` and does nothing. Expiry judges a return that was held back (:100-109). The broker runs Unlock past a stuck `busy` once `checkRunning()` expires it, and never clears a newer check's `busy` (FreshAuth.kt:77-88). Nothing leaks: the AppLock singleton gets one Handler post per check. A failed or cancelled check returns false, so nothing is sent. A late *Passed* is a genuine biometric pass, so unlocking on it is fine. Closed.
- NITs: ports are 8760 plus the typed port (LanDiscovery.kt:186); §15 has the SDK 37 NSD-resolve note (protocol.md:1012-1014); `SessionsScreen` `pcId` has no default (SessionsScreen.kt:89). Closed.
- Trial relay: it uses the pinned `clientFor` (ServerClient.kt:87-88), so the Bearer token (RelaySocket.kt:55) goes out only after the pin is verified. A forwarder sees ciphertext only. The trial socket is **not** bound to Wi-Fi, same as every relay: under a full-tunnel VPN it can send one ClientHello into the tunnel (IP literal, no SNI, no token), and the pin fails. Acceptable.
- TL1d: names are `Aristotle on <host≤39B> (<8hex>)` and `aristotle-<host≤44>-<8hex>`. The hint is never cut, the host is cut on a rune boundary, and the target is ASCII a-z0-9-. Packets over 9000 B are dropped first, using a 9001-byte buffer. A 33rd question is dropped as it is parsed, before any answer. The 8 hex add nothing the TXT `fp` (16 hex) does not already publish. OK.

## Findings
- **MAJOR-2 (new, functional regression of Q65's main case): with Tailscale up, discovery never runs.** Android refuses `Network.bindSocket` to a physical network for an app covered by a VPN that is not bypassable, whatever its routes are (netd `checkUserNetworkAccessLocked`, `isSecure()`). Tailscale does not call `allowBypass()` (Google issue 569667436; johnmaguire.me "camera connection issues with Android VPNs"). So `routeOf` throws, `ScanGate` returns `Unavailable`, auto-find skips (LanDiscovery.kt:429), and a manual search shows "Can't scan this Wi-Fi". That is exactly the "online over Tailscale → move to LAN" case. The 2.5 s device fact came from the unbound TL1 build. Not device-verified (no adb). Check: Tailscale on, tap Find → if it shows "Can't scan", confirmed. Fix: on a refused bind with a VPN as default, take an unbound route when (i) the VPN's `LinkProperties.routes` match no target (no 0/0 and nothing covering the Wi-Fi prefix, `RouteInfo.matches`) and (ii) the VPN's underlying network is this Wi-Fi (`TRANSPORT_WIFI` and not cellular, or `getUnderlyingNetworks` on API 31+). Split-tunnel traffic falls through to that network, as the relay's already does. Full-tunnel VPNs and lockdown stay refused. Add a gate test.
- MINOR-A (bounded DoS by an on-link forwarder that reaches the PC): (1) If the trial fails **before** the 4409 arrives (a forwarder resets right after the upgrade; LAN beats the tailnet path), `trial` is already null at :378-379. The 4409 then hits `endWhileTrying(.., null)` (:362, :400-404) → `Superseded` → a 60 s stand-down. The test (LinkManagerTest `theServerSuperseding…`) covers only the 4409-first order. Fix: remember in `onlineOn` that a trial ran, and map a later 4409 to `Switch`. (2) A forwarder that passes ready is stored as lastGood (:440). If it then keeps dropping the relay after each ready, `reached()` (:351) resets the backoff every time, and on that Wi-Fi Tailscale is never tried. This is equivalent to an ARP-spoofing on-link host; consider not resetting the backoff for a relay that dies within a few seconds. Trials happen only on a discovery (Wi-Fi join or tap), never in a loop of their own.
- NIT: NSD is not scoped to the Wi-Fi (`discoverServices` without a `Network`; API 33+ can scope it); the on-link filter and the bound checks make this harmless. Pre-34: freeing the slot at 3 s while the platform resolve is still active makes the next resolve hit FAILURE_ALREADY_ACTIVE (that service is skipped). `endWhileTrying` blocks network wakes for up to 20 s.

Not verified: device behaviour (bind under Tailscale or other VPNs, NSD, the trial against a live server).
