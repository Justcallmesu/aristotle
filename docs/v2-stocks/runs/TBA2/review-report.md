## Findings
- **MAJOR-1 — Brief page day chips: before the brief runs, the newest kept brief cannot be opened and the wrong chip shows as selected.** `BriefScreen.kt:202-216` treats `list[0]` as "the latest" (`selected = i == 0`; a tap on it calls `pick(null)`). On a trading day before 08:30, `latest` is the made-up `pending` today, which is not in `/briefs`. So yesterday's chip shows selected while the page shows "Comes at 08:30", and tapping it shows `pending` again. With a single kept brief (`size > 1` fails) there are no chips at all. Fix: select by date: `selected = row.date == (state.picked ?: state.latest?.date)`. Tap: `pick(row.date.takeUnless { it == state.latest?.date })`. Show the chips when `list.any { it.date != state.latest?.date } || list.size > 1`. Put this in `BriefUiState` and add a test with `latest = pending today` and `list = [yesterday]`.
- **MINOR-2 — Brief card on a trading day:** (a) when `/jobs` has not answered (`jobs == null`) and the brief job is off, the card reads "Not a trading day" (`Brief.kt:111-113`). Fix: return `Unknown` while `briefJobOn == null` and the latest brief is older than today. (b) When the brief job is turned on after its slot, the server answers `pending` all day (`scheduler.go:402-405` marks the slot handled with no `Missed` call), so the card reads "Comes at 08:30" at 14:00. Fix: in `card`, pass the WIB time and treat `pending` at or after 09:00 as "No brief today". Alternatively the server could only make up `pending` before 09:00; that is a TBA1b contract note.
- **MINOR-3 — Unpair race:** `stockAlerts.clear()` runs before the credentials are wiped (`AppContainer.kt:338-343, 357-359`). A long-poll answer arriving in that window calls `take()`, which writes the old PC's cursor and feed back and may post a notification after the second tray sweep. Fix: call `stockAlerts.clear()` again inside the launched block after `wipeActive()`/`records.unpair()`, as `clearAlerts()` already does.
- **MINOR-4 — The Q109 wiring is untested:** `AlertsTest` covers only the 3-argument boolean. A mutation of `AppContainer.kt:286-290` (for example `appVisible = true`) survives. Fix: make the combine pure (`AlertPolicy.target(c, l, visible, keep): AlertTarget?`) and test it with keep on/off, Stop, unpaired and HermesDown.
- **MINOR-5 — A burst re-alerts:** `postStockAlerts` posts every alert in an answer one by one (`AppContainer.kt:302-306`). Three alerts for one code give three heads-ups on a HIGH channel. Fix: post only the newest alert per tag (its `lines` already list the rest), or use `setOnlyAlertOnce(true)` for the repeats.
- **MINOR-6 — The page's pending line ignores the job time:** `briefStatusLine` uses the constant `"08:30"` (`BriefScreen.kt:300`), while the card uses the job's `at`. Fix: pass `state.jobs?.job(BRIEF)?.at`.
- **NIT:** focus rows open `focus.code` without `StockCodes.valid` (`BriefScreen.kt:269`). The `StockOpen` → stack mapping is duplicated (`AristotleApp.kt:306-322`); extract `StocksBackStack.open(StockOpen)`. A repeat tap pushes the same Brief or Alerts page twice. `StockAlertsViewModel`/`AlertsScreen` live in `BriefViewModel.kt`/`BriefScreen.kt`, and `StockNotices`/`StockOpen` live in `AlertWatcher.kt`; one file per responsibility would be clearer. `AlertWatcherTest.kt:128-129` asserts `count == calls.size` straight after reading it, so it guards nothing. A pending `stockOpen` is not cleared on unpair.
