## Findings
- **MAJOR-1 — a picked day sticks for the life of the process, and with the pending latest there is no way back.** `picked` is reset only by a chip tap. `BriefViewModel` lives in the process-wide stocks store (`AristotleApp.kt:564-566`), and `open(Brief)` on the Brief page is a no-op. So after the user looks at an older day once, Home's card and the "Today's brief is ready" notification open that old brief. Days later it is the same. The MAJOR-1 case (latest = made-up `pending`, list = [yesterday]) makes this worse. After a pick, the only chip is yesterday, already selected, so the latest can never be reached again. The new test codifies exactly that state (`BriefDayChipsTest.kt:20-24`).
  Probe on the copy: `chips at open [04 pick=04]` → `pick 04` → leave/re-enter → `page on re-entry: 2026-11-04 latest=2026-11-05` (FAILED expecting 05).
  **Fix:** reset `picked` to null whenever the page is entered by navigation (a `BriefViewModel.opened()` called where `open(StockOpen.Brief)` is shown, including a repeat tap or a notification). When `latest.date` is not in `list`, prepend a chip for the latest (`pick = null`). Add a VM test for pick → leave → open, and a chips test for pending latest + [yesterday] after a pick.
- **MAJOR-2 — `setOnlyAlertOnce(stockShown(tag))` silences every later alert of a code while the earlier one is still in the tray** (`Notifier.kt:113`). The notification auto-cancels only on a tap, and the server allows 3 notified alerts per code per day (§20.4). So a 09:10 setup alert left unread makes the 14:00 "BBCA hit your stop" a silent update: no sound, no heads-up. That defeats Q104/Q18 alerts. The burst it targets is real: the server wakes the long-poll per appended item (`alerts.go:300-304`), so one scan arrives in several answers milliseconds apart. But that needs only a short window.
  **Fix:** quiet only when the tray copy is recent. Use a pure `StockNotices.quietUpdate(shownPostTime: Long?, now: Long)` (e.g. < 60 s) fed from `StatusBarNotification.postTime`, with a test for "minutes later → alerts again".
- **MINOR-1 — the page's pending line is not cut at 09:00** (`BriefScreen.kt:264-268`). The card says "No brief today", and tapping it opens a page that says "Comes at 08:30". A regression is certain in that case. Cheapest guard: one pure `BriefStates.status(body, now, at)` that both the card and `briefStatusLine` use, tested at 08:59 and 09:00.
- **MINOR-2 — the unpair double clear narrows the race but does not close it, and nothing tests it.** The watcher runs on `linkScope` = `Dispatchers.Default` (`AppContainer.kt:138`). After `poll` returns, `take()` and `notify` do not suspend, so they can still run after the second `clearStockState()` and the tray sweep. The MINOR-3 test calls the store by hand and passes on the old code, so it guards nothing. Removing either `clearStockState()` call survives.
  **Fix:** add a generation to `StockAlertStore`. `clear()` bumps it; the watcher reads it before `poll`; `take(gen, …)` drops a stale answer, writes nothing and notifies nothing. Test it in `AlertWatcherTest` with a real held call.
- **NIT:** In `AlertsTest`, "Stop from the notification, app closed" repeats the previous assertion verbatim. The `open(Stock)` same-code branch is redundant (`openStock` on a stock page already returns an equal copy), so its test cannot fail. The KDoc `(\\\"08:30\\\")` at `BriefViewModel.kt:56` has literal backslashes. There is a double blank line at `BriefScreen.kt:70-71`. The home card's 09:00 cut is read only on recomposition, so an idle screen keeps "Comes at" past 09:00. `stocks_brief_late`/`missed` hard-code 08:30, but the brief job's time is editable (05:00-08:45).
- **Not seen RED (builder admits):** acceptable. The PM mutations killed M1 and M2, and by reading, the Q115 tests (`BriefTest.kt:81-98`) and the target tests fail under the obvious mutations. The exception is the MINOR-3 test (above).

VERDICT: CHANGES-REQUIRED (MAJOR-1 stuck picked day, MAJOR-2 later same-code alerts silenced; MINOR-1/2 recommended)
