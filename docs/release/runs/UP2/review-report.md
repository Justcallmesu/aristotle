# UP1 + UP2 review (fresh reviewer, deep): server app-update endpoints + phone in-app updater

## Verified
- Read the full uncommitted diff, the spec (Q132-Q134, P17-P20), the UP0/UP1/UP2 briefs and reports, and pm-check.log. Server copy in scratch: gofmt clean, `go vet` ok, `go test -race ./internal/httpapi -run App` and `./internal/config` PASS. I did not run Gradle: the PM gate already ran it (1468 unit tests, exit 0).
- **Trust chain holds.** Only the paired PC can supply an APK. The updater uses the per-pin `HttpClients.pinnedTo` client: `PinnedTrustManager` and the pinned hostname verifier, `followRedirects(false)`/`followSslRedirects(false)`, `Proxy.NO_PROXY`, the Bearer token. A captive portal or other host fails TLS, and a 3xx response is a BadStatus. LAN and Tailscale each get their own client and pool. Before install the phone checks, in order: sha256, then package, then the signer set (empty set never matches), then that the APK is newer. Even a compromised PC cannot push an APK signed by someone else.
- **TOCTOU risk is low.** The sha256 is computed over the exact bytes written to `cacheDir/update/`, which only this app can write. `inspect` and the session read that same path. Android verifies the v2/v3 signature again over the whole file. The only path where file and hash can differ is the double-launch in MINOR 1.
- Signer comparison uses `apkContentsSigners` on both sides. This matches Android's own update rule for one or several signers. An APK with a rotated key (v3 lineage) would be refused (OtherSigner), which is acceptable because no rotation is planned. `GET_SIGNING_CERTIFICATES` with `PackageInfoFlags` is correct for API 33+, and the deprecated overload covers minSdk 29. Equal and lower versions are refused both in the rules (AppUpdate.kt:65) and in ApkCheck (P20).
- Install flow: explicit intent to a non-exported receiver, and `FLAG_MUTABLE` is used only on 31+ (allowed on 34 because the intent is explicit). `setAppPackageName` is set. On commit failure the session is abandoned. The `STATUS_*` mapping matches the platform constants. The INSTALLING marker is a durable write before commit, so "Updated to x.y.z" is shown only when own code ≥ target.
- Server: fixed file names, no traversal, symlinked file must be a regular file. Both routes sit behind `requireDevice`, and `remoteHandler` gives both listeners the same router. `http.ServeContent` streams from the file with no buffering, and there is no WriteTimeout to cut a 35 MB download. Pair-swap race: install.sh writes the APK first and the json last. During that window a request sees the new APK with the old json: the size check gives 204, or, if the sizes happen to match, the phone's hash check refuses the file. Fails safe either way. An already-open fd keeps the old inode.
- Cadence works with Hermes down (`serverEndpoint` also covers HermesDown/HermesUpdated). Each version notifies once (stored code, `>` rule). EN and ID strings are complete (43 each).

## Findings
- **MAJOR** android/app/src/main/AndroidManifest.xml:19 (AppInstaller.kt:58): `UPDATE_PACKAGES_WITHOUT_USER_ACTION` is not declared. The platform docs for `setRequireUserAction` list it as a condition ("The installer declares the UPDATE_PACKAGES_WITHOUT_USER_ACTION permission"; normal permission, API 31+). Without it every update gets STATUS_PENDING_USER_ACTION, so Q133 (no tap) can never happen. With it, a self-update qualifies ("Updating itself") from the first OTA on. Fix: add the `<uses-permission>`.
- **MAJOR** AppInstaller.kt:124-137 + AppUpdates.kt:231-235 + UpdateRow.kt:37: if the confirm screen never shows, the row stays "Installing" with no button, and `busy()` blocks Update. This happens when PENDING_USER_ACTION arrives while the app is in the background, which is the common case on HyperOS. The 35 MB download takes long enough that the user leaves the app. The receiver's `startActivity` is then blocked silently by background-activity-launch rules (no exception, so `confirm` returns true), or the user leaves the confirm screen with Home and no status ever arrives. The foreground LinkService keeps the process alive, so only a force-stop clears it. Fix: keep the `EXTRA_INTENT` and give the row a "Confirm install" button on resume, and/or post it as a notification action. Let `Installing` fall back to Retry, for example after the next resume with no status.
- MINOR AppUpdates.kt:207-215: `update()` checks `busy()` synchronously, but `Downloading` is set only after the launch on `Dispatchers.Default` (AppContainer.kt:148, AppUpdates.kt:272). A double tap, or a tap during `permissionReturned`, starts two runs. They write the same file, `running` keeps only the second job, and the file one run verified can be truncated or deleted by the other. Android's signature check limits the damage to a failed install. Fix: set the step (or a guard) before `launch`.
- MINOR AppUpdates.kt:168-186: a disconnect while a check is running cancels it inside `collectLatest` and `checking` stays true. The row then shows "Asking your PC…" with Check now disabled until the next connect. Fix: reset it in `finally`.
- MINOR AppUpdates.kt:168-173: every id→null→id flap of the link triggers a new check, with no minimum interval. A reconnect loop therefore means one GET plus one server info log line (appupdate.go:108) per flap. Not a storm with link backoff, but suggest a floor (e.g. 15 min per PC unless "Check now").
- MINOR AppUpdates.kt:207-208 + UpdateRow.kt:38: if the PC installs a new release between the check and the tap, the download fails with HashMismatch. Retry reuses the stale offer and fails again, and the Failed+available state shows no Check now, so the row is stuck until reconnect or the 6 h check. Fix: send `If-Match: "<sha>"` (ServeContent answers 412), or re-check on HashMismatch.
- MINOR strings.xml:1492 (+ ID): "Aristotle restarts when it is done" is not true. Nothing relaunches the app or LinkService after the package is replaced: there is no `MY_PACKAGE_REPLACED` receiver. Session and stock alerts stay off until the user opens the app, which matters more once tap-less installs work. Fix: add the receiver or reword the string.
- MINOR scripts/install.sh:89 vs :169-170: a bad APK file name exits 1 after `install_binary` has already replaced the binary. This contradicts the header ("refuses before touching anything"). Also :46: only `aristotle-server` must be listed in SHA256SUMS, so an unlisted APK would be copied and served unverified. release.sh does list it. Fix: validate and require the APK inside `verify_bundle`.
- NIT appupdate_test.go:139: `TestAppUpdateLogsOnceAndNeverThePath` never asserts the path is absent, and appupdate.go:110 logs `err.Error()`, which includes the path for a `PathError` (e.g. EACCES). It is not a secret, but the test name claims more than it checks.
- NIT ApkCheck.kt:22: the archive's versionCode is not compared with the announced `version_code`. If they differ, the "Updated to" line (keyed on the announced code) does not show.
- Open (not code): Q133 on HyperOS is still unobserved (UP0 blocked). Re-run the UP0 spike with the permission above added.
