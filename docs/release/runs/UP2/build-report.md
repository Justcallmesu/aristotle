# UP2 build report: phone in-app updater
- Check (P18): `data/update/AppUpdates.kt` asks `GET /v1/app/update` when a PC connects (aristotle-server is enough, Hermes can be down) and every 6 h while connected. A different address of the same PC does not count as a new connection. The pure rules in `AppUpdate.kt` offer only `version_code` > `BuildConfig.VERSION_CODE`. They treat 204, an equal code and a lower code (rolled-back server, P20) as up to date, and any other status or a body that breaks the contract as a failed check.
- Show (Q132): new row under Settings › About › Version (`ui/settings/UpdateRow.kt`). It reads "Update x.y.z available" with an Update button, or "Up to date · x.y.z" with Check now, then shows download progress, checking, installing, or the reason it stopped (EN and ID). New "App updates" channel `app_updates`: IMPORTANCE_LOW and silent, one notification per version (the code is stored), cancelled when the PC reports up to date. Tapping it opens About through the non-exported alias (`OpenUpdate.kt`).
- Download (`AppUpdateHttp.kt`): starts only on a tap and uses the pinned client and token from `HttpLinkDialer` (LAN and Tailscale). Saves to `cache/update/`. Hashes with sha256 while streaming. The announced `size` is a hard cap: a larger Content-Length is refused before reading, and extra streamed bytes stop the copy. The file is deleted on failure, cancel, refusal and after commit, and the folder is emptied at start.
- Verify (P18, `ApkCheck.kt`): sha256 must match, the archive must be readable, the package must be ours, the `apkContentsSigners` SHA-256 set must equal ours (Android reports archive signers via `GET_SIGNING_CERTIFICATES`), and the APK must be newer. A failure shows a clear reason in the row.
- Install (P19, Q133, `background/AppInstaller.kt`): a `PackageInstaller` session with `setAppPackageName`, and `USER_ACTION_NOT_REQUIRED` on API 31+. Manifest adds `REQUEST_INSTALL_PACKAGES` and a non-exported `UpdateInstallReceiver`; the status PendingIntent is explicit and mutable on 31+. If `canRequestPackageInstalls()` is false, the row explains why and Allow opens `ACTION_MANAGE_UNKNOWN_APP_SOURCES`; once the user is back with it allowed, the update continues. On PENDING_USER_ACTION the app starts `EXTRA_INTENT`. Failures (aborted, blocked, storage, refused) show in the row. A success is shown after the restart as "Updated to x.y.z" (the target code is written with a durable commit first).
- UP0 (read at the end): the phone runs Android 14/API 34 with HyperOS. The spike used the same API shape as this build. Q133 is still unanswered, and on-device behaviour of this updater is NOT verified (no adb, as instructed).
- Contract checked against UP1's protocol §21: `/v1/app/apk` 204 or any other non-200 is treated as BadStatus.
- Tests, RED first (compile failures on the missing API and the updated `NotifyChannelsTest`): `AppUpdateRulesTest` (10), `ApkCheckTest` (6), `ApkStreamTest` (5), `AppUpdateHttpTest` (8, MockWebServer with pin), `AppUpdatesTest` (13), `UpdateRowLogicTest` (2), `OpenUpdateTest` (2). All green.
- Not done (outside my whitelist): the `docs/protocol.md` phone-side note and the CHANGELOG entry. `PackageInstaller`/`PackageManager` glue is untested on a device. The confirm screen opens only while the app is in front (Android background-start rules).
- Gate after the last edit: `GATE_ONLY=android bash docs/v1-tickets/gates.sh docs/release/runs/UP2` → PASS android, PASS licences, exit 0 (1468 unit tests).

CHANGELOG "Doc text" (Phone line):

Tap Update to download it over your paired connection, checked against its checksum and the app's own signature, then install it. Android asks once to allow installs from Aristotle.
