# DS1 build brief — server `--json` + `start|stop|restart`

Repo: `/home/justcallmesu/project/personal/Aristotle` (read `PROJECT.md` first). Spec: `docs/desktop/spec.md`
(decisions D10, P9, P11, P12; read the whole file). Ticket text: `docs/desktop/tickets.md` § DS1.

## Why
A Tauri desktop app (later ticket) will control the server only by running `aristotle-server <cmd> --json` (D10).
Go must stay the only owner of the output shapes; the app parses what you emit. So the JSON is a contract.

## Goal
1. `--json` flag on: `status`, `version`, `devices list`, `terminal status`, `pair`, and on the actions
   `devices revoke <id>`, `devices grant-terminal <id>`, `devices ungrant-terminal <id>`, `terminal enable`, `terminal disable`,
   and the new `start`, `stop`, `restart`.
2. New commands `start`, `stop`, `restart`: `systemctl --user <verb> aristotle-server` through `service.Manager`
   (`server/internal/service/service.go:133-136` `ctl`, add small methods there; tests use the existing stub Runner).
3. `stop` and `restart` refuse inside an Aristotle remote terminal (P12): same detection as `scripts/install.sh:58-61`
   (env `ARISTOTLE_TERMINAL` set, or `/proc/self/cgroup` names `aristotle-server.service`); make the cgroup file path and env
   injectable for tests. `start` is allowed. Refusal: exit 1 with a clear message (JSON `{"error":...}` under `--json`).

## Output contract (write it into `docs/protocol.md` as a new short section "CLI JSON output (desktop app)")
- Success: exactly one JSON object on stdout + newline, nothing else on stdout. Exit code identical to the plain command.
- Failure: `{"error":"<text>"}` on stdout, same non-zero exit code as the plain command; nothing on stderr except a usage
  error (exit 2) which may keep today's usage text on stderr.
- Shapes = the control results that already exist, not new ones: `statusResult` (`server/internal/app/controlcmds.go:124-150`),
  `terminalStatusResult` (`server/internal/app/terminalcmds.go:53-61`), `devices.Public` (`server/internal/devices/devices.go:46-51`),
  `pairStartResult` (`server/internal/app/controlcmds.go:28-33`) **plus** `qr_payload` (string = `pairing.Payload(code,
  fingerprint, urls)` with ALL addresses up to `pairing.MaxPayloadAddresses`, see `qrFor` in `server/internal/app/cli.go:100`).
  `devices list --json` = `{"devices":[...]}` (an object, not a bare array, so fields can be added).
- `status --json` must answer when the server is down: wrap service facts and the control result, e.g.
  `{"service":"<is-active>","enabled":"<is-enabled>","server":"running|not-running|no-answer","result":{...}|absent}`.
  Mirror exactly what `status --porcelain` decides (`printPorcelain`, `server/internal/app/servicecmds.go:191`); reuse its
  logic, do not fork it. Exit code identical to plain `status`.
- `version --json`: `{"version","commit","protocol"}` from `server/internal/version/version.go` (read how `Line` builds it).
- `start|stop|restart --json`: `{"ok":true,"service":"<is-active after>"}`.
- Field names snake_case like the existing json tags. Times RFC 3339 (Go default).

## Invariants
- Plain (non-`--json`) output of every existing command is unchanged byte for byte. Add golden tests for the plain output
  of each touched command BEFORE changing code, see them pass on the old code, keep them passing.
- `pair --json` writes the code only to stdout; never to stderr, the server log, or an error string.
- One small helper for "print JSON result / JSON error" used by every command; no copy per command.
- No new dependencies. Std lib only.
