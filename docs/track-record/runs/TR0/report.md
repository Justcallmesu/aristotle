1. **Past 5-minute bars (A1).**
 - V: the client cannot ask for a past session as shipped. `Yahoo.Chart(code, rng)` sends only `range`+`interval` (`yahoo.go:196-204`), and `ChartRanges` maps 1d→5m, 5d→15m, 1mo→1h (`provider.go:~117`). `Market`/`Provider` have no period1/period2 path, so TR needs a new method (e.g. `Provider.Intraday(ctx, code, from, to)` + fake in tests).
 - V (probe): `…/v8/finance/chart/BBCA.JK?interval=5m&period1=<day 00:00 WIB>&period2=<+24 h>` returned 200 for 1 back (2026-11-05, 67 bars), 5 back (10-30, 55), 20 back (10-09, 55) and 40 back (09-11, 55; 56 calendar days). A 70-day-old day (08-28) returned **HTTP 422** (`UpstreamError http 422`; body not read), consistent with Yahoo's 60-day 5m limit that `provider.go` comments. The exact cut-off between 56 and 70 days is A (probe once at ~60 days).
 - V: one request may span many days: 10-26..11-06 → 591 bars, 9 sessions, one call.
 - V coverage: a Mon-Thu session has 67 bars, first 09:00, break gap 11:55→13:30 (no 12:00-13:25 bars); a Friday has 55 bars, first 09:00, gap 11:25→14:00. Both have a gap 15:45→16:00 (the 15:50 pre-closing bar is null and dropped by `bars()`, `yahoo.go:~245`) and **last bar 16:10** (the 16:00/16:05/16:10 closing-auction bars exist). So the bars cover 09:00-16:10 WIB. Lunch-break bars never appear.
 - V missing day: Sunday 11-01 → 200, 0 bars, no error (a holiday is assumed to look the same, A). Too old → 422. An unknown symbol → 404 `ErrUnknownSymbol`.
 - A: the 16:20 bars job can already see the day's final 5m bars (probe covered finished days only; the bars job's own 1y daily fetch comes at 16:20). Confirm with a probe at 16:25 on a trading day.
2. **Ordering rule.** V: bars are OHLC per 5 min, so entry/target/stop can be ordered across bars but not inside one bar. Proposed rule, walking bars oldest first, only bars with `t + 300 > analyzed_at` when the call was made during the session (see 8a):
 - Entry: the first bar with `L ≤ entry_high && H ≥ entry_low` triggers; none → not triggered (Q118). Fill = `min(entry_high, max(O, entry_low))`.
 - The trigger bar: `L ≤ stop` → stop first (loss); otherwise a target touched in it does NOT count (it may have come before the fill); scoring continues from the next bar.
 - Later bars: both `H ≥ target` and `L ≤ stop` in one bar → stop first (Q119 conservative); otherwise whichever is touched; neither → settle at the session close (daily close).
 - A target reached before the entry zone was touched (price gaps up through the target, then falls back into the zone) ignores that earlier touch: only post-fill touches count.
 - If the 5m fetch fails or is empty, a day that touches both levels counts stop first (Q119). Hold/Avoid/Sell/Wait use the same walk or the close.
3. **`session_date` (Q120b).** V: set from `Indicators.SessionDate` (`analyzer.go:662`), computed by `SessionDate(now)` (`indicators.go:137-143`): today if it is a trading day and `now` is before 16:00 WIB, else `NextOpen(now)`'s date. So before 09:00, during the session and in the 11:30/12:00-13:30/14:00 break → that day; 15:50-16:00 → that day; after 16:00 → next trading day; weekend/holiday → next trading day. Q120b's reading is correct. `market_state` is `Status(now).State` (open/break/closed, `idxcal.go`).
4. **Bars coverage (A2).** V: yes. `postAnalyze` only checks `codeRe` (`analyzer.go:326-339`, `http.go:48-54`); `preflight` calls `dailyBars`, which uses the store only when fresh and otherwise `Market.Chart(code,"1y")` (`bars.go:~207-215`, `analyzer.go:~455`). Any IDX code works. For the scorer: V, the 5m window of a session (plus the next 3 sessions for the Q117 info column) comes from ONE period request per code (probe: 9 sessions = 1 call, 591 bars, ~40 KB). That also yields session O/H/L/C/close, so no daily bars are needed for a non-quoted code. Cost: 1 request per distinct code with calls in the batch, paced 1.5 s like `barsPace`; for a quoted code the 3-day close can come from the store (0 requests). ≈ ≤10 requests/day at 10 calls/day.
5. **Kept results today.** V from code: `stocks-analyses.json` = `{"version":1,"analyses":{CODE:result},"failed_sessions":[]}` (`analyzer.go:~160-166`), at most 50 codes, one result each (`maxAnalyses`, `:33`). Every field scoring needs is in `AnalysisResult` (`:119-147`). Gaps: results kept before TBA1 have `trigger` empty, normalized to `manual` on load (`:263`), which can mislabel an old auto result (none could exist before TBA1, so harmless, but `model` of old results is A). There is no `rule`, no score, and no history: at most one verdict per code. I did NOT open the real file (`~/.local/state/aristotle/stocks-analyses.json` exists; forbidden by the brief), so the live count and age range are unknown (A; PM can run `jq '.analyses|length'` on it). Seed value is small: ≤ 50 records, mostly sessions after ~Nov 2026.
6. **Size.** V (measured with a script, compact JSON, no reasons/news): 281 B per verdict record; 447 B with a score block (outcome, exit, close, pct, order source, 3-day close, `rule`, scored_at). At 10/day: ~4.5 KB/day, ~1.1 MB per 250 trading days (1.6 MB per 365 days). Recommendation: no cap on records now; keep the load-time size guard (e.g. 8 MiB, like `maxBarsFileBytes`) and rewrite atomically; revisit at ~5 years. Rewriting a ~1 MB file per `keep`/score pass is fine; an append-only JSONL would avoid rewriting but `statefile.WriteAtomic` is the repo's pattern, so keep JSON.
7. **Scheduler hook.** V: `bars.daily` is `{At:"16:20", TradingDays:true, CatchUp:CatchUpAlways, MinAt:"16:15"}` (`stocks.go:148-149`); its run also calls `screenEOD` and may end with a partial `JobError` (block). Recommend its own job `track.score` (`TradingDays:true`, `At:"16:30"`, `Wanted` = some unscored call whose session has completed), not a step inside `runBarsDaily`: a Yahoo block or partial run of the bars job then cannot fail scoring, scoring failures cannot fail the bars job, and the 5m fetch is a different endpoint. Catch-up: `CatchUpAlways` (not the Q31 default "before 16:00", which would mean never for a 16:30 job), because the scheduler runs only the latest slot (`scheduler.go:28`) and one run must score ALL unscored sessions (oldest first), and because the 60-day 5m limit makes a long outage lossy. `Wanted` should also require `barsFresh` only if the 3-day column reads the bar store.
8. **Spec vs code.**
 - a) Look-ahead gap: Q117 "window = the session" does not say what a call made at 14:00 does with the 09:00-14:00 bars. The code stores `analyzed_at` and `price`; the scorer must ignore bars before the call (`t + 300 ≤ analyzed_at`), else a morning touch of the entry zone would count as a fill. Calls made before 09:00 or after 16:00 use the full session.
 - b) A1 is understated: the real limit is ~60 days (422 at 70 d), not "at least ~30"; a call older than that cannot be 5m-ordered, so it falls back to Q119's stop first (only matters for sessions that touched both levels).
 - c) Holidays: the bundled list holds only 2026 dates from 12-24 on (`idxcal.go:~24`, "dates still ahead when written"), so earlier 2026 holidays read as trading days: a call made on the evening before such a holiday gets a `session_date` that has no bars (e.g. 2026-08-17). The scorer must treat an empty session (0 bars, also empty daily) as "no session: carry to the next trading day or void", never as a loss, and not rely on `IsTradingDay` for past dates.
 - d) Q119 "fetched once after close": needs the per-code period fetch above (new `Provider` method; the Q116-Q120 text assumes a path that does not exist yet). The 16:00-16:10 closing-auction bars exist and move the close; use the daily close for "close at end of window".
 - e) `price` in a result is quote price, else the last 5m close, else the last close (`indicators.go:180-189`): after the close it is that day's close, so an Avoid/Sell made after 16:00 compares the NEXT session's close to the previous close, which is what Q120 intends.
 - f) Q120a "buy at entry high": consistent with the fill rule in 2 (entry_high, or the open if it gaps lower).
